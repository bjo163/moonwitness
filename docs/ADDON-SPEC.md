# MoonWitness Addon Specification

Status: **Canonical addon contract**.

An addon is a self-contained business/domain module that plugs into MoonWitness through explicit models and dependencies.

## Standard shape

Recommended package layout:

```text
packages/moon-<addon>/
├── package.json
└── src/
    ├── index.ts
    ├── models/
    │   ├── *.ts
    │   └── ...
    ├── routes.ts        # optional: only non-generic endpoints
    ├── services/        # optional: only domain orchestration that does not belong on a model
    └── tests/
        └── ...
```

Do not create folders merely to match the template. Optional folders should exist only when needed.

## Manifest

`src/index.ts` is the backend addon manifest and public package entry.

Example:

```ts
import CabProject from './models/cab-project.js'
import CabChange from './models/cab-change.js'

export { CabProject, CabChange }
export { registerCabRoutes } from './routes.js'

export default {
  name: 'cab',
  description: 'Change Advisory Board',
  depends: ['base'],
  models: [CabProject, CabChange],
}
```

Rules:

- `name` is stable and unique
- `depends` lists only direct addon dependencies
- `models` contains the models registered by the addon
- imports must not create cyclic addon dependencies

## Model ownership

Every persistent domain concept should have one owning addon/model.

Example:

```ts
import { Vertex, fields } from '@moon/orm'

export default class CabChange extends Vertex {
  static _name = 'cab.change'
  static _description = 'CAB Change Request'

  title = fields.Char({ required: true, size: 180, index: true })

  status = fields.Selection({
    selection: [
      ['draft', 'Draft'],
      ['submitted', 'Submitted'],
      ['approved', 'Approved'],
      ['rejected', 'Rejected'],
    ],
    default: 'draft',
    index: true,
  })
}
```

Business validation, domain invariants, model lifecycle behavior, and model-level permissions should live with the model/addon rather than in generic HTTP handlers.

## CRUD policy

Ordinary CRUD/query behavior should use generic model REST/RPC generated by `moon-server` and Moon ORM.

Do not create custom routes such as:

```text
POST /cab/create-change
GET  /cab/list-changes
PUT  /cab/update-change/:id
```

when the same operation is already represented by generic model operations.

Custom routes are appropriate when the operation is a real domain action, for example:

```text
POST /api/cab/change/:id/approve
POST /api/mizan/case/:id/evaluate
POST /api/witness/:id/verify
```

Even custom routes must call model/domain behavior rather than writing directly to PostgreSQL.

## Database access

Default rule:

```text
addon -> model -> Moon ORM -> PostgreSQL
```

Direct `getDb()`, Knex, or raw SQL from domain addon code is not the normal path.

If direct SQL is genuinely required for a specialized query, migration, or performance-sensitive operation:

- keep it isolated
- preserve access rules where applicable
- preserve transaction semantics
- add tests
- document why ORM primitives are insufficient

## Transactions

Multi-record domain operations must run inside a Moon ORM transaction.

A route must not simulate a transaction by passing a normal database connection into the `trx` field of `Ctx`.

Domain side effects that must be atomic with a write belong inside the same transaction. External/non-transactional side effects should be triggered only after a successful commit or through a reliable queued/outbox mechanism when introduced.

## Security

Addon models inherit the platform security contract:

- authenticated users receive only explicitly granted access
- missing/invalid grant configuration fails closed
- record rules use controlled domain data
- arbitrary JavaScript in persisted rules is prohibited
- special public access must be explicit

Do not implement a second addon-specific authorization framework unless the domain has an additional rule that cannot be represented by the common model security system.

## Routes

`routes.ts` is optional.

When present, routes should be thin:

```text
parse/auth context
      |
      v
call model/domain method
      |
      v
map result/error to HTTP
```

Routes should not own database transactions, duplicate validation, or encode the only copy of a business rule.

## Services

A `services/` layer is optional, not mandatory.

Create a service only for real orchestration spanning multiple models or external systems when placing the behavior on one model would be misleading.

A service must not become a generic repository abstraction around Moon ORM.

## Cross-addon communication

Preferred order:

1. call the dependent addon's registered model through `env.getModel(...)`
2. use an explicitly exported domain function where a model call is not appropriate
3. use events/async integration only when decoupling is genuinely needed

The dependency must be listed in the addon manifest.

## Testing expectations

Each important addon should cover:

- model creation and validation
- relation behavior
- permissions/record rules
- transactional domain actions
- custom routes, if any
- addon registration and dependency boot

CAB will be used as the reference addon while the architecture is hardened.

## Anti-patterns

Avoid:

```text
addon-specific ORM
addon-specific repository layer
business logic in generic server handlers
direct DB writes from UI/server routes
custom CRUD endpoints duplicating generic REST
hidden dependencies between addons
arbitrary executable code stored as security rules
new framework packages for a single use case
```

## Definition of a healthy addon

A new developer should be able to understand an addon by reading:

```text
index.ts
models/
(optional) routes.ts
```

If understanding the addon requires tracing several generic service/repository/runtime layers, the design should be simplified before adding more abstractions.
